# RF π licensing & selling guide (vendor-only)

This is the operator's guide to the built-in licensing system. It is for
**you** (K4DIA) as the vendor; buyers never see it.

## How it works

RF π ships two kinds of software and the license system only touches one:

- **The RF π suite** (dashboard, field tools, logbook, artwork) — your
  proprietary code. This is what the license gates.
- **The bundled open-source apps** (WSJT-X, fldigi, Direwolf, CHIRP, …) —
  free software under their own licenses. **Never** gated. They keep working
  on an expired trial, and `OPEN-SOURCE.txt` on the image documents this.

Enforcement is **off by default** and only turns on when a vendor public key
(`/etc/hampi/vendor.pub`) is present in the image. So the open GitHub build
stays a normal free/dev build; only images you build with your key enforce.

Licenses are **offline Ed25519-signed tokens**. A key encodes the buyer's
callsign, name, and issue date, signed by your private key. The Pi verifies
the signature with the embedded public key — **no activation server, no
internet** — which is non-negotiable for an off-grid field device. The key is
bound to the callsign, not the hardware, so one license covers a buyer's shack
Pi, go-box, and tablet, and a leaked key visibly names its owner.

Trial: full-featured for `TRIAL_DAYS` (default 14) from first boot. On expiry
the RF π suite locks behind an activation screen; the logbook can still be
read and ADIF-exported (a buyer's data is never held hostage).

## One-time setup

```bash
cd ham-radio-pi
# 1. Generate your signing keypair (KEEP vendor/vendor.key SECRET & BACKED UP)
python3 scripts/rfpi-keygen.py --init
# 2. Point buyers somewhere; set your store URL and contact
nano payload/configs/vendor.conf        # PURCHASE_URL=, CONTACT=, TRIAL_DAYS=
```

`vendor/vendor.pub` is safe to commit and is baked into every image you build
(`prepare-stage.sh` copies it in; `setup.sh` installs it to
`/etc/hampi/vendor.pub`). `vendor/vendor.key` is **gitignored** — it is the
entire business; anyone with it can mint licenses. Back it up offline.

## Issuing a license after a sale

```bash
python3 scripts/rfpi-keygen.py --call K4ABC --name "Jane Ham" --email jane@example.com
# prints:  RFPI1.<payload>.<signature>
```

Email that string to the buyer. They paste it into the dashboard's activation
screen (or drop it at `/var/lib/hampi/license.key` and restart `hampi-dash`).
Verify any key with `python3 scripts/rfpi-keygen.py --verify "RFPI1.…"`.

For **pre-activated SD cards**, write the buyer's key to
`/etc/hampi/license.key` on the card before shipping — it boots licensed.

## Selling channels

See the full market/pricing plan (separate doc) for the strategy. In short:
a self-hosted checkout or a storefront like Lemon Squeezy (native license-key
delivery, acts as merchant of record for tax) sends the buyer a key; you can
automate issuance by having its purchase webhook call `rfpi-keygen.py`.
Physical SD cards go on eBay/Etsy/at hamfests. Nothing here depends on any
specific store — the keys are yours, generated by your script, verified on the
device with no third party in the loop.

## Before you sell

1. **Take the suite private.** `ham-radio-pi/` is in a public repo now; move it
   to a private repo so the source isn't freely cloneable.
2. **Legal review.** The proprietary-suite / GPL-apps split is sound (the GPL
   explicitly permits selling copies; you add no restrictions to the GPL
   software), but have a lawyer confirm before launch. `LICENSE-RFPI.txt` and
   `OPEN-SOURCE.txt` are the buyer-facing notices that make the split explicit.
3. **Keep the source offer.** For the GPL apps you redistribute, you must offer
   corresponding source. Pointing at the Debian/upstream archives (as
   `OPEN-SOURCE.txt` does) satisfies this for stock packages.
